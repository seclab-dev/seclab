# 通知中心架构

## 职责边界

通知中心是当前登录用户需要持续关注的信息集合，不是 Toast 历史，也不是操作日志副本。它只接收后台任务终态、安全事件和系统事件。页面校验、同步请求结果、列表加载失败等即时反馈仅由前端内存 Toast 展示，不会持久化。

Master 是通知的唯一生成与查询事实来源。客户端没有创建、修改通知内容或永久删除通知的接口。操作日志仍保存完整的可信状态变更；通知中心只投影事件注册表明确允许的事件。

## 领域模型

每条通知绑定 `recipientUserId` 和唯一的 `operationEventId`，内容创建后不可变。用户只能改变以下状态：

- `readAt`：未读或已读。
- `archivedAt`：活跃或归档；恢复时保留原读取状态。
- 超过 90 天后由系统维护任务分批清理。

通知内容由稳定通知码、分类、关注级别、结果、来源、目标、任务标识和白名单参数组成。关注级别由注册表按事件语义计算，使用提示、警告和严重三个等级，不从操作结果直接推断。结果只用于后台任务终态；节点离线、恢复和安全事件等通知不携带无业务意义的操作结果。详情可以包含脱敏且限长的错误摘要和追踪标识，但不会保存原始请求、响应、命令、环境变量、凭据、完整路径集合或任意元数据。

## 生成流程

操作事件写入 Master 时，在同一数据库事务内查询通知注册表并完成个人投影：

1. 注册表判断事件、终态与结果是否允许生成通知，并独立计算关注级别及结果是否需要投影。
2. 按发起用户、计划任务所有者或全部活跃管理员确定收件人。
3. 只保留该通知码允许的基础参数，并由后端计算安全跳转动作。
4. 以收件人和操作事件唯一约束保证 Agent 重试、重复上报和终态恢复不会生成重复通知。

未注册事件仍可进入操作日志，但不会产生通知。投影失败不会改变已经完成的业务操作，Master 会写入英文运行日志以便诊断。

Agent 只接受 Master 通过机器信任链注入的用户标识，并将其与最终操作事件一起写入持久 outbox。外部同名请求头会被移除，Master 接收事件时以认证节点覆盖来源节点身份。

## 接口与隔离

通知接口位于 `/api/v1/notifications`：

- `POST /query`：分页和组合筛选当前用户通知。
- `GET /unread-summary`：查询未归档通知的未读数量和版本。
- `GET /{notificationId}`：按需查询详情。
- `PATCH /{notificationId}/read-state`、`POST /read-all`：修改读取状态。
- `PATCH /{notificationId}/archive-state`、`POST /archive-state`：归档、恢复单条或最多 100 条通知。

所有查询和变更由认证用户 ID 强制隔离。不存在和不可见统一返回 404；非法分页、筛选、时间范围或批量大小返回稳定的 400 领域错误。列表固定按创建时间和通知 ID 倒序排列。

## 前端生命周期

Shell 登录后立即获取未读摘要，页面可见时每 30 秒静默刷新一次，并禁止请求重叠。失败时保留旧角标，不产生 Toast。登出会停止轮询并清空用户状态。

通知中心列表、详情和未读摘要分别执行 latest-request-wins。首次失败、空通知、筛选无结果、归档为空和后台刷新失败是不同页面状态；刷新失败会保留已有数据。打开详情会幂等标记已读，归档未读通知会立即从角标移除，恢复后按原读取状态重新计数。

## 保留与迁移

本模型从 Alpha 阶段直接生效：现有迁移中的旧通知表和旧应用 ID 已被替换，不迁移旧数据，也不保留旧接口、旧类型或兼容字段。已有开发数据库需要按项目的 Alpha 数据重建流程重新初始化。
